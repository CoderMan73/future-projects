# Research: mkw-race-tracker

Citation key:
- [CO] Concept, `E:\Coding_Projects\future-projects\public\concept\mkw-race-tracker\CONCEPT.md`.
- Web sources are linked inline. Discovery date: 2026-10-18.

## 1. Executive summary

Partially unique: the concept's data model (track ID, grid/finish position, per-player finish times, single-player classification) is fully documented by the community and a working autosplitter already dereferences the same structs, but every existing tool targets a different target than Retro Rewind on Wiicompiled. No existing project reads the `RetroRewind.exe` process memory externally and writes per-race single-player results to a log (JSON Lines). Confidence: high that no such tool exists on the searched packages/registries (section 3); the one structural uncertainty is the address-resolution mechanism for the Wiicompiled native binary (section 6, item 1).

## 2. Existing solutions survey

1. LiveSplit Mario Kart Wii autosplitter (zormy111/mario-kart-wii-autosplitter, `maryk-splitter.asl`) — a LiveSplit ASL script that reads race memory to drive speedrun splits and an in-game timer. It reads Dolphin's emulated MEM2 (signature-scans for the MEM2 base, then dereferences `ptr + 0x000009BD730` for `Raceinfo::sInstance`). It does not log per-race results to a file, and its target is the Dolphin process (`Dolphin.exe`), not `RetroRewind.exe` or Wiicompiled. Status: unmaintained (last push 2019), ASL, source embedded in the `.asl`. Evidence it works: it dereferences the Raceinfo player array and the `raceFinishTime` Timer pointer and byte-swaps the minutes/seconds/milliseconds, matching `mkw-structures` offsets.
2. mkw-ana (Wiimm) — `mkw-ana.wiimm.de` / https://github.com/BS157/mkw-ana — analyzes the MKWii network protocol from a tcpdump/Wireshark capture of Wii traffic; it prints live race tables and writes per-race result files (MakeDoc/PHP). It does not read process memory at all; it operates on network packet dumps. Online-only, requires mirroring Wii network traffic to the PC.
3. MKW Renn-Statistik (wiimm.de/mkw-race) — a live online statistics site backed by mkw-ana; same network-capture model, not a memory reader.
4. rewind-overlay (MichaelAccount1/rewind-overlay) — a third-party overlay reading Retro Rewind online room/leaderboard data from RWFC API endpoints ("No account, token, scraping, or memory injection"). Online-only, API-based, not a memory reader and not single-player.
5. MKWTracker (sc0tt/MKWTracker) — 2012 Python project (1 star, archived) that "tracks Mario Kart Wii Wifi Race Sessions." Last push 2012; unmaintained, no documented memory layout, purpose unknown beyond its description; predates Wiicompiled by a decade.
6. Wiimm's network protocol documentation — https://mkwiiki.org/wiki/Network_Protocol/RACEDATA — describes the RACEDATA network record (positions, speed, inputs) sent between console and server. Network protocol, not host-process memory; out of scope for the external reader.
7. Dolphin Memory Watcher — dolphin-emu/dolphin Core/MemoryWatcher (commit tamamadesu/dolphin 2f50560) — a Dolphin feature that emits changed watch-address values to a Unix socket; not a standalone tool and not a Wiicompiled reader.
8. Dolphin-memory-engine (aldelaro5/dolphin-memory-engine) / py-dolphin-memory-engine — a RAM search/Editor GUI and Python library for reading Dolphin's emulated memory. Targets the Dolphin process specifically (MEM1/MEM2 base discovery via the emulator's own region detection), not a native recompile.

## 3. Uniqueness verification

- No tool that targets `RetroRewind.exe` (Wiicompiled) and logs per-race single-player results was found. Section 2 item 1 (the autosplitter) reads the structurally identical `Raceinfo`/`Racedata` structs, but only from Dolphin's MEM2 and only to drive a speedrun timer; items 2-6 never read host-process memory at all.
- The Retro Rewind distribution itself ships no race logger. Its in-game telemetry surface is limited to Discord Rich Presence (https://mkwiiki.org/wiki/Retro_Rewind), which reads character/game-mode/track/current VR/BR from inside the process; no external logging mode is exposed.
- `RetroRewind.exe` is a real shipped binary: SteamDB entry `3552140` lists `RetroRewind.exe` (https://steamdb.info/app/3552140), and the Reshade MKWii mod confirms installation path `AppData\Roaming\CT-MKWII\Recomp\Install\RetroRewind\RetroRewind.exe`, identifying it as a Wiicompiled static recompile (x86-64). So the target process exists.
- Negative evidence is bounded: searches covered GitHub, mkwiiki, mariokartwii.com forums, the Retro Rewind Discord, SteamDB, and general web search for `RetroRewind.exe` + `ReadProcessMemory` / race logger. Confidence is high that no published memory-based single-player race logger for Wiicompiled exists, because any such project would intersect the same well-indexed communities (mkwiiki, mariokartwii.com, Retro Rewind Discord) where the autosplitter and mkw-ana are cataloged.

## 4. Gap analysis

Where existing solutions fall short of this concept, precisely:

1. Wrong target process. The autosplitter reads Dolphin's emulated RAM (base discovered via MEM2 signature scan); mkw-ana/rewind-overlay/network-protocol tooling never touch host memory. None reads `RetroRewind.exe` (Wiicompiled) memory externally, which is the concept's explicit target.
2. No per-race result logging to JSON/structured output. The autosplitter produces only speedrun timer splits; mkw-ana's result files are online-room oriented. The concept requires a per-race JSON Line (timestamp, track, mode, players with character/vehicle/finish position/finish time) written after each single-player race.
3. No single-player gating by process. Existing readers assume a known process state; the concept must poll for `RetroRewind.exe`, classify Grand Prix vs. Time Trial vs. everything else via `gameMode` + `localPlayerCount`, and log only single-player offline races.
4. Closed-source anti-cheat in the target. Retro Rewind ships a closed-source anti-cheat that "blocks most common and basic cheat attempts" (https://mkwiiki.org/wiki/Retro_Rewind, "Retro Rewind Anti-Cheat"). Whether read-only external memory inspection is treated as a cheat attempt is unknown (section 6, item 2).
5. No graceful address handling. Existing tools fail hard on bad addresses. The concept explicitly requires failing gracefully when expected addresses do not contain valid-looking data (CONCEPT.md section "Known constraints").

The data the concept needs is itself well-documented and not a gap: `mkw-structures` documents `Racedata` (`racedata.h`), `Raceinfo` (`raceinfo.h`), and the `Timer` struct, and the PAL static addresses (`0x809BD728` Racedata::sInstance, `0x809BD730` Raceinfo::sInstance) match exactly between CONCEPT.md and `raceinfo.h`/`racedata.h`. The autosplitter proves the dereference + big-endian byte-swap path for `RaceinfoPlayer.position` and the `raceFinishTime` Timer works in practice.

## 5. Foundation candidates (ranked)

1. SeekyCt/mkw-structures — the data model. Fit: canonical, community-maintained documentation of the exact structs the concept dereferences (`Racedata`, `RacedataSettings`, `RacedataScenario`, `RacedataPlayer`, `Raceinfo`, `RaceinfoPlayer`, `Timer`). PAL addresses match CONCEPT.md. 46 stars. Caveat: `MenuData` offsets are not documented here (the concept's `0x809C1E38` is cited as community/gecko-code source, not in this repo), and NTSC-U/J/K alternative offsets are out of scope for MVP.
2. zormy111/mario-kart-wii-autosplitter — the read technique. Fit: the only end-to-end reference that follows the `Raceinfo -> players[] -> RaceinfoPlayer -> raceFinishTime -> Timer` chain and applies PowerPC big-endian byte-swapping; its pointer arithmetic is the direct template for the dereference loop. Caveat: hard-coded to Dolphin's MEM2 base (`ptr + offset`), so its address math does not transfer verbatim to Wiicompiled.
3. PyMemoryEditor (https://pymemoryeditor.readthedocs.io, pypi PyMemoryEditior, v3.4.0, MIT) — the memory-access layer. Fit: pure-Python (ctypes) cross-platform reader/writer/scanner for Windows, Linux, macOS; supports `read_process_memory`, typed reads, `search_by_addresses`, pointer chains, and zero-copy `read_process_memory_into` for the polling loop; matches the concept's Windows-primary + optional-Linux scope. Caveat: it reads raw bytes, so PowerPC big-endian decoding is the tool's responsibility (the autosplitter confirms this is needed).
4. pymem (https://pymem.readthedocs.io) / PyMemory (GabeMillikan/PyMemory) — Windows-only `ReadProcessMemory` ctypes wrappers (pymem's API mirrors CONCEPT.md's Windows path directly). Lower fit than PyMemoryEditor because they are Windows-only and the concept allows a Linux reader; keep as fallback only if a pure-ctypes dependency is disallowed.
5. Wiicompiled (patchzyy/Wiicompiled, https://github.com/patchzyy/Wiicompiled) — the target. Fit: required background to confirm whether the Wii `0x80XXXXXX` range is mapped literally in the host process. Caveat: static recompiler with no in-repo memory-layout docs for external readers; the address-resolution question must be resolved against a running build (section 6, item 1).

## 6. Unknown areas

1. Does Wiicompiled map the Wii `0x80XXXXXX` range at a literal, fixed host address in `RetroRewind.exe`? CONCEPT.md asserts it maps "the entire 4 GB Wii address space into the host process at a fixed, deterministic base address" so the tool "simply adds a fixed offset to any known Wii address" with "no runtime base-resolution step." Wiicompiled is a static recompilation targeting x86-64 (https://github.com/patchzyy/Wiicompiled), and the host process is `RetroRewind.exe` (SteamDB 3552140). Whether that literal mapping holds for a native recompile (vs. allocating a relocatable MEM1/MEM2 buffer requiring a one-time base discovery like Dolphin) is not documented in the Wiicompiled repository or mkwiiki. Resolved by inspecting the running process's virtual memory layout for a region containing a known MEM1 marker byte pattern and checking whether `0x809BD730` is directly dereferenceable. This gates milestone 2 and any address choice in the plan.
2. Does Retro Rewind's closed-source anti-cheat block or flag read-only external memory inspection of `RetroRewind.exe`? The anti-cheat "blocks most common and basic cheat attempts" (https://mkwiiki.org/wiki/Retro_Rewind) but its behavior toward an external `ReadProcessMemory` reader is unspecified. Resolved by testing against a live build and observing whether reads succeed / the process is unaffected.
3. NTSC region offsets. CONCEPT.md states PAL addresses and that NTSC-U/J/K variants "have known alternative offsets." The PAL set is confirmed against `mkw-structures`; NTSC alternatives are community-documented but not independently verified here. Resolved by adding a region flag and validating against mkwiiki's address tables before any non-PAL support.
4. `MenuData`/`RaceinfoPlayer` finish-timer pointer validity window. The autosplitter notes `raceFinishTime` is only populated after a player finishes (CONCEPT.md section on finish times), and `MenuData`/`scene` is the only source for race-start/end boundaries. Scene-state detection from `MenuData` is community-attested but its exact offset is not in `mkw-structures`. Resolved by cross-checking the autosplitter's scene/stage handling and the community `Some Useful Memory Strings` thread for the menu vs. race transition.
