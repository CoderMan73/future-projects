# Plan: Craftraria - genuine Terraria inside a Minecraft Java Edition mod

> Derived from CONCEPT.md and grounded in RESEARCH.md. Implementation starts only after explicit approval; relocation from `concept/` to `planned/` happens only on approval.

## Objective

A Fabric mod for Minecraft 1.26.2, structured like craftlatro, that lets a player run the real Terraria from inside Minecraft on a flat in-game GUI screen. The player supplies their own Terraria `Content` directory; the mod serves the wasm port (velzie's "Terrarium", MercuryWorkshop/terraria-wasm release 1.0) plus the player's staged assets over a local COOP/COEP HTTP server to an embedded Rinku Chromium browser. The page stages the assets into OPFS, the recompiled game runs at 1-to-1 behavior, and saves persist across sessions. No Re-Logic code or assets are bundled or distributed by the mod.

## Goal / Motive / Purpose

A second, independent app in the browser-embedded family, so the browser-embedded-runtime pattern reads as a product line rather than craftlatro being the library itself. Terraria qualifies the same way Balatro did: a commercial C#/FNA game with no JVM runtime path, whose full-fidelity portable build is a community wasm port. This purpose constrains every decision below: integration glue only, no game code or assets in the jar, vanilla-only, single-player, flat GUI only. Anything that does not serve "run the real Terraria in-game with the least new machinery" is out of scope for v1.

## Chosen path

Reuse the craftlatro architecture wholesale (Rinku embed + local COOP/COEP server + player-supplied game files + mod-written served page), and swap the game runtime from love.js to the Terrarium wasm port, with the Balatro.exe-to-.love extraction replaced by a server-side tar of the player's `Content` directory plus an OPFS staging page. Rationale: RESEARCH.md Section 5 ranks craftlatro's proven core (candidate 1) and Rinku (candidate 2) as the strongest foundations, and Section 4 Gap 1 shows the only genuinely new integration problem is the asset handoff, which the upstream's own simple-download flow solves with plain `fetch` and needs no browser picker (Gap 1, Section 2 asset flow). Rebuilding the game in Java is not a candidate: no JVM path exists (RESEARCH.md Section 2).

## Target stack and tooling

- Loader: Fabric, Minecraft 1.26.2. Matches Rinku branch `26.2.0` in the local source tree and craftlatro's proven matrix (RESEARCH.md Section 2).
- Browser: Rinku, coordinate `de.keksuccino:rinku-fabric:3.0.5-26.2` from `https://keksuccino.github.io/maven/` (local source: `MCSourceCode/Rinku` branch `26.2.0`, `mod_version=3.0.5`). Same public API surface craftlatro documented in `docs/rinku-api-notes.md`.
- Java toolchain: craftlatro builds on Java 21 with Rinku 3.0.4-26.2. Local Rinku 3.0.5 source declares `java_version=25` in its own build (Rinku `gradle.properties`). Verify the resolved artifact's class-file version at M1 and pin the mod's toolchain to match; do not assume 21 still works with 3.0.5.
- Build: Gradle with Fabric Loom 1.15.5 (`fabric_version=0.153.0+26.2` per Rinku source).
- Config UI: Cloth Config as a hard dependency, Mod Menu compile-only, matching craftlatro's stack decision.
- Game runtime: MercuryWorkshop/terraria-wasm release `1.0` asset `terraria-wasm-build.zip` (36,314,788 bytes; `_framework` 134.9 MB uncompressed; verified to contain engine plus recompiled game code and no assets). Downloaded at runtime by a `TerrariaBuildDownloader` (the `LoveJsDownloader` pattern), verified, and unpacked to `<instance>/craftraria/game/build/`, never into the repo or the jar. Release 1.0 is pinned; the fact that master is newer than the release is recorded in `ai-docs/decisions/pin-terrarium-build.md` with the tradeoff (RESEARCH.md Unknown areas, build provenance).
- Asset staging: the mod packs the player's `Content` directory into a tar served by `LocalHttpServer`; the served page fetches and extracts it into OPFS (upstream `extractTar` flow, reproduced in vanilla JS in the mod-written page). The `Content` copy lives under `<instance>/craftraria/game/` and is generated from the player's own install path (recorded like craftlatro's `balatroExePath`).
- Served page: a mod-written vanilla-JS page (no bundler) reproducing upstream's `preInit` glue (dotnet config with `pthreadPoolInitialSize: 16`, the jiterpreter runtime options, module imports where still applicable) and the `PreInit`/`Init(width, height)`/`MainLoop` sequence, modeled on upstream `src/game/index.ts` (RESEARCH.md Section 5, candidate 4). `sw.js` is stripped from the served copy (RESEARCH.md Section 4, Gap 2).
- Legal guardrails: only accept a player-supplied Terraria install; never bundle, extract, or distribute Re-Logic code/assets; the wasm build is fetched by the player's client at runtime from GitHub, the same posture as the love.js player (craftlatro AGENTS.md "Never"; upstream README: "Do not publicly host the game assets without permission from Re-Logic. This is for personal use only.").

## Milestones and steps

### M0: Process setup (before any code)

- Clone the craftlatro conventions into the new repo: AGENTS.md (stack table, verification ladder, Windows dev notes, gotchas, boundaries), `docs/commits-and-releases.md`, CHANGELOG (Keep a Changelog), conventional commits, release runbook, `ai-docs/` structure. Copy the craftlatro gotchas that are already proven so they are not re-derived: never `createBrowser(url, transparent, width, height)` for a fresh browser, never a surface larger than the window's own full-screen size, park (mute + 5 fps + shrink) rather than close, Rinku pumps paints for every live browser, one browser-affecting change per user verification run.
- AGENTS.md Context Loading names `E:\Coding_Projects\MCSourceCode` (`Rinku`, `vanilla-minecraft/26.2`, `cloth-config`, `fabric-api/26.2`) as the first source for API/version questions, web search as fallback. This is the post-mortem's F1 lesson (three redirects across three sessions).
- Set up the repo skeleton (src/main + src/client layout mirroring craftlatro) and the release-only CI workflow.

### M1: Scaffolding, Rinku integration, and environment probes

- Scaffold the Fabric 1.26.2 mod with Loom; resolve Rinku 3.0.5-26.2; pin the Java toolchain after checking the artifact's class-file version.
- Port craftlatro's core embed classes: `TerrariaBrowser` (screen-agnostic singleton with parked state), `BrowserScreen`, `BrowserWindow`, `LocalHttpServer` (COOP/COEP as-is). The headers are identical to craftlatro's: `Cross-Origin-Embedder-Policy: require-corp`, `Cross-Origin-Opener-Policy: same-origin` (upstream `public/_headers`; craftlatro proven note).
- **Probe first, before game work** (each probe is a standalone, agent-runnable check where possible, per the verification ladder): (a) a probe page served through `LocalHttpServer` that writes and reads a file in OPFS via `navigator.storage.getDirectory()`; (b) the same page reporting availability of `showDirectoryPicker`, `showOpenFilePicker`, and `navigator.keyboard.lock` inside Rinku's Chromium; (c) load release 1.0's `_framework` unmodified through the server and reach `Program.PreInit()`'s `mount_opfs()` call. Record results in `ai-docs/notes/2026-MM-DD-jcef-environment-probes.md`. These close RESEARCH.md Unknown areas 1, 2, and 4 and de-risk everything downstream.

### M2: Build downloader and serving pipeline

- `TerrariaBuildDownloader`: download the pinned release zip from GitHub at runtime with a progress path, verify size (36,314,788 bytes), unzip to `<instance>/craftraria/game/build/`, refresh only when the pin changes. Nothing from the build goes into the jar.
- Serve `_framework` unmodified through `LocalHttpServer` (version-pinned URLs; `index.html` `no-store`; strip `sw.js`). Verify the dotnet runtime initializes through the local server (M1 probe c proves the path; this milestone makes it the real thing).
- `TerrariaPaths`: one class resolving every instance-local path, mirroring `CraftlatroPaths`.

### M3: Player-supplied Content handoff

- Directory acquisition, reusing craftlatro's shape: `SteamLocator`-style detection of the Terraria install (default Steam library paths plus `libraryfolders.vdf`), JFileChooser fallback with the headless guard, and a `/craftraria load <path>` command. Record the path in the game dir like craftlatro's `balatroExePath`.
- **Version experiment, run first.** Release 1.0 is a May 2025 decompile of a pre-1.4.5 game, and the only evidence that newer `Content` breaks it is issue #15, a bare unanswered report from the day 1.4.5 shipped. Loading is code-driven (the recompiled binary asks only for asset names it knows, and Terraria's `Content` is cumulative across updates), so current-version content may well load. Stage the player's actual install as-is against the pinned build and record the outcome in `ai-docs/notes/<date>-terraria-version-experiment.md`: which Terraria version, whether the menu, world generation, and a save round-trip all work, and any asset errors verbatim. Treat version mismatch as test-then-warn, not as a hard block. If current content loads, there is no constraint to communicate to players; if it fails, see the mismatch flow below.
- **Version mismatch UX.** When the experiment shows the detected install does not work (or is later reported not to), the mismatch screen names the installed version and the supported version and hands the player the exact remedy, not a generic warning: open the Steam console (`steam://nav/console`), then `download_depot 105600 <depot_id> <manifest_id>` with the depot ID and manifest ID for the supported version taken from the depot/manifest history listed for Terraria on SteamDB, then point the mod at the downloaded depot folder (its `Content` folder) via `/craftraria load <path>`. The command text and the IDs are shown pre-filled in the warning screen and repeated in the config screen, so the player copies rather than researches. Their live install is untouched by this; the rolled-back content is a separate folder.
- Validation: the selected directory must be (or contain) `Content` with `Fonts`, `Images`, `Sounds` (upstream `validateDirectory`); report the detected Terraria version from the install. GOG installs have no depot rollback equivalent, so the mismatch flow covers Steam and GOG users are told plainly that the owner-side rebuild fallback applies (see Key risks).
- Packaging: generate a tar of the player's Content into `<instance>/craftraria/game/content.tar` with a version marker (mtime/size keyed), served by the local server; the served page fetches the tar, extracts it into OPFS, and writes the `.ContentExists` marker, reproducing upstream's flow. Path separators are a known hazard: issue #17 notes Terraria requests assets with backslash paths (`Images\UI\X`) while emscripten splits only on `/`; probe extraction early and record the outcome.
- Standalone probes (craftlatro P1 pattern): a probe that validates a directory and a probe that round-trips the generated tar, so the packaging logic is verified without launching the game.

### M4: Game launch, screen, input, and performance

- The mod-written page: PreInit (OPFS mount, `/Content` symlink handling happens inside the game), then `Init(width, height)` and `MainLoop`. The window/notice design carries over from craftlatro: the game sizes itself at page load (upstream takes `screen.width/height` at Init), so a window change offers a reload strip rather than forcing one, and no surface is ever larger than the window's own full-screen size (the Rinku async-paint crash boundary).
- Input: Minecraft keyboard/mouse mapping into the browser (craftlatro's `BrowserScreen` mapping); keyboard-first per the concept. `navigator.keyboard.lock` availability (M1 probe) decides whether the key-swallow preamble from upstream `src/game/index.ts` can be used. Gamepad: research and decide (JCEF gamepad support versus GLFW-level mapping), defaulting to out-of-scope for v1 unless M1 probes say otherwise.
- Performance knobs and the stats report, ported from craftlatro: paint-rate control capped to Minecraft's measured fps, render scale, and a `/craftraria stats` diagnostics report that separates target from applied values. Measure Terraria-in-Chromium-in-Minecraft fps and memory against the ~168 MB heap figure reported upstream (issue #17) and craftlatro's 144-to-130 measurement.

### M5: Saves, warnings, packaging, and release guardrails

- Save persistence: saves live in the browser's OPFS at `/libsdl/tsaves` and persist in the Chromium profile. Implement export/import as the mod-served page's own tar-in/tar-out UI (upstream OPFS explorer as reference), or a profile-directory copy if the M1/M4 probes justify it; record the decision and the tradeoff in `ai-docs/decisions/`.
- First-run warning: fidelity and support disclaimer (port status, the supported version range as settled by the M3 experiment, upstream open issues #17/#13/#16, no multiplayer, no tModLoader), styled like craftlatro's `FidelityWarningScreen`. When a version mismatch is known, this screen carries the pre-filled depot-rollback command and the SteamDB IDs rather than a bare "unsupported version" message.
- Packaging guardrail: a build-time check that fails if any Re-Logic binary or asset is staged; the jar contains mod classes and the served page only.
- Conventions: conventional commits; `gradle.properties` one-line versioning; release runbook with local `clean build check` as the only gate; Ask First on tags/releases.

## Key risks and unknowns

- **OPFS or the File System Access API misbehaves inside Rinku's Chromium** (RESEARCH.md Unknown areas 1-2). This is the linchpin of M3. Mitigation: M1 probes before any asset work; fallback design is already chosen (no browser picker anywhere in the flow), so the worst case is an OPFS workaround to research, not a redesign.
- **`_framework` does not load cleanly through the local server** (dotnet.js asset resolution, split-wasm loader) (Unknown area 4). Mitigation: M1 probe c; fallback is a release-1.0-specific patch step in the served copy, recorded like craftlatro's four-bug-stack note.
- **Supported Terraria version is narrow and unverified** (Gap 4): release 1.0 (May 2025) is a pre-1.4.5 decompile, and the only breakage evidence (issue #15) is thin and unanswered. Resolution order, not a single guess: (1) the M3 version experiment runs the pinned build against the player's actual content version, and if current content loads there is nothing to warn about; (2) if it fails, the player-side remedy is the Steam depot rollback the mod spells out exactly (console command plus SteamDB depot/manifest IDs, then point at the downloaded folder), which keeps the live install intact; (3) a player-run build from the upstream toolchain is not a realistic player task and is not the plan's remedy; if a rebuild is ever genuinely required it is an owner-side decision, evaluated by building once locally, and publishing such a build for players would change the project's legal boundary from "player's own copy" to "we distribute a recompiled game" and would put the rebuild pipeline in this project's hands permanently. That call, if it comes, is an explicit owner decision.
- **Upstream defect surface lands on the player** (Gap 5): world-entry crash (#17), missing splash asset (#13), broken archive button (#16) are open upstream. Mitigation: pin release 1.0, record repro notes for upstream reports, and keep the mod's own surface (server, screen, cache pinning) as the only things under this project's control.
- **Cache layers serve stale state** (Gap 2): `sw.js` plus OPFS plus dotnet caching. Mitigation: strip the service worker, version every served URL, `no-store` on the loader page, and treat "the fix did not take" as a cache question first (the `440f734` reflex).
- **Performance/memory** (Gap 7): AOT wasm plus 135 MB of framework plus Chromium plus Minecraft in one process. Mitigation: M4 measurement with the stats report; paint-rate cap and render scale from day one.
- **Interactive verification runs through the player only** (craftlatro F5): the screen opens on a real input event the agent cannot synthesize. Mitigation baked into the plan: standalone probes wherever the logic allows, the stats report as the hand-back instrument, and at most one browser-affecting change per user run, each named with exactly what to check.

## Handoff boundary

This plan is complete at RESEARCH.md + PLAN.md and waits for explicit user approval before relocating `public/concept/craftraria/` to `public/planned/craftraria/`. Implementation (scaffolding, downloads, builds, code) begins only on a separate explicit request. The boundary between planning and implementation is the M1 probe suite (OPFS read/write, picker/keyboard-lock availability, `_framework` load through the local server): if those probes pass, the milestones proceed; if any fails, the affected design decision is re-opened with the probe evidence rather than assumed.
