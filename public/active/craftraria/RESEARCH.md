# Research: Craftraria - genuine Terraria inside a Minecraft Java Edition mod

> Discovery run per the `dont-reinvent-the-wheel` snapshot at `SKILLS/concept-to-plan/references/dont-reinvent-the-wheel.md` (snapshotted 2026-10-09T17:43:30Z). Scope: browser-in-Minecraft Chromium embeds plus real Terraria wasm ports. Sources: `concept/craftraria/CONCEPT.md`, the craftlatro project (repo, git history, ai-docs, post-mortem), the local `E:\Coding_Projects\MCSourceCode` tree, and primary upstream repositories. Run date 2026-10-14.

## 1. Executive summary

The idea is **partially unique with strong reusable foundations on both halves**. No existing project runs genuine Terraria inside a Minecraft Java mod. The two required ingredients exist separately and are composable, exactly as in craftlatro: the embed layer (Rinku) is already proven in production by craftlatro, and the game runtime is a real wasm port of Terraria (MercuryWorkshop/terraria-wasm, "Terrarium", by velzie with r58Playz) that runs the decompiled-and-recompiled game in a browser from user-supplied assets. Confidence: high that the specific combination does not exist; the remaining work is the same class of integration glue craftlatro already shipped, with new unknowns around the asset handoff into the browser and the upstream port's version support.

## 2. Existing solutions survey

### Browser-in-Minecraft (Chromium embed)

The craftlatro discovery already mapped this space (`E:/Coding_Projects/future-projects/public/active/craftlatro/RESEARCH.md`, section 2). Findings carried forward unchanged:

- Rinku (library). Fabric + NeoForge, MC 1.26.2, Chromium 151.x (CEF commit-pinned), LGPL-2.1, published to `https://keksuccino.github.io/maven/` as `de.keksuccino:rinku-fabric:<v>-<mc>`. Local source at `E:\Coding_Projects\MCSourceCode\Rinku`, branch `26.2.0`, `mod_version=3.0.5`, `minecraft_version=26.2`, `jcef_commit=2eb4ca2648bda91d1dfed81e9a37ba92e757aff9`, `fabric_version=0.153.0+26.2`, `fabric_loom_version=1.15.5` (verified from `gradle.properties`). craftlatro ships on this stack at v0.9.1 with the flat-GUI browser pattern proven hands-on (`ai-docs/notes/2026-10-12-lovejs-pipeline-proven.md`).
- WebGUI, Browsermod, Client Web Displays, MCEF, WebDisplays: end-user embed apps with no programmatic porting surface for a game runtime; surveyed in the craftlatro research, same conclusions apply.

### Terraria in the browser (wasm port)

- MercuryWorkshop/terraria-wasm ("Terrarium"), https://github.com/MercuryWorkshop/terraria-wasm, homepage https://terraria.mercurywork.shop. "Terraria ported to the browser with WebAssembly." 193 stars, created 2025-02-02, master last pushed 2025-06-16, 118 forks, no license file, 9 open issues. Single release `1.0` (2025-05-17): asset `terraria-wasm-build.zip`, 36,314,788 bytes, 3,206 downloads, published by user `velzie`. Port credited to velzie with r58Playz (writeup: https://velzie.rip/blog/celeste-wasm). Build path (verified from the repo): `ilspycmd` 9.0.0.7889 decompiles the player's `Terraria.exe` (plus the embedded `ReLogic.dll` extracted from the game), patches are applied, and the result is recompiled to wasm via .NET 9 (`Microsoft.NET.Sdk.WebAssembly`, `TerrariaWasmAot=true`) against r58Playz's FNA-wasm statics (`FAudio.a`, `FNA3D.a`, `libmojoshader.a`, `SDL3.a`, `libcrypto.a` fetched from `r58Playz/FNA-WASM-Build`).
- Release contents verified by downloading and inspecting the asset: `_framework/` (105 entries, 134.9 MB uncompressed) containing `dotnet.js` (stable name), `dotnet.runtime.*.js`, `dotnet.native.*.js`, `dotnet.native.*.wasm` (95.5 MB single chunk in this release), `dotnet.native.worker.*.mjs`, and the game assemblies under hashed names (largest: `terraria.htgijktbe2.dll` 19.4 MB, `SteamKit2` 6.1 MB, `System.Private.CoreLib` 2.2 MB). No `Content/` directory: **the release ships engine plus recompiled game code and zero game assets.** Frontend chrome: `index.html`, `assets/index.js` (217 KB bundled frontend), `assets/index.css`, `sw.js` (service worker), `AndyBold.ttf`, `app.ico`, `logo.png`, `backdrop.png`, and a `MILESTONE` file containing a single git hash (`d5f6e8959593395bda9dea415aa5bf4deb7ca218`).
- Asset flow (verified from `src/fs.tsx`, `src/splash.tsx`, `terraria/Program.cs`): the page exposes three paths, (a) "Copy local assets": `showDirectoryPicker()` selects the Terraria `Content` directory (validated: must contain `Fonts`, `Images`, `Sounds`), which is copied into the page's Origin Private File System (`navigator.storage.getDirectory()`); (b) "Download assets from Steam": SteamKit2 compiled to wasm logs in (username/password or QR) through a Wisp proxy and downloads the depot; (c) "Extract archive": a `.tar`/`.tar.gz` is fetched (or picked) and extracted into OPFS. The C# side then calls `mount_opfs()` at PreInit, symlinks `/Content` to `/libsdl/Content`, and sets `SavePath = "libsdl/tsaves"`; the game is driven from JS via `Program.PreInit()`, `Program.Init(screen.width, screen.height)`, `Program.MainLoop()`. A simple-download build mode exists (`VITE_SIMPLE_DOWNLOAD=true VITE_SIMPLE_DOWNLOAD_FILE=/terraria-wasm.tar`) where the page fetches a tar from the server and extracts it into OPFS with no browser picker at all (code present but commented in the Makefile).
- r58Playz/fna-wasm-threads, https://github.com/r58Playz/fna-wasm-threads, "A template for porting FNA games with threads." MIT, 5 stars, last push 2026-04-14, updated 2026-09-17. The engine template the port is built from; relevant only if a local rebuild is ever needed.
- MercuryWorkshop/celeste-wasm, https://github.com/MercuryWorkshop/celeste-wasm, "Browser port of Celeste (2018) and Everest using WebAssembly." 267 stars, no license, default branch `threads-v2`, pushed 2026-08-26. The sibling project underpinning the craftleste concept; not a craftraria foundation.

## 3. Uniqueness verification

Claim: running the real Terraria inside a Minecraft Java mod does not already exist.

Evidence:

- The browser-in-Minecraft ecosystem (Rinku, WebGUI, Browsermod, CWD, MCEF) embeds Chromium generically; none integrates a game runtime, and none combines with Terraria anywhere in their documentation.
- The only real Terraria-in-browser runtime is Terrarium (velzie). Its own frontend is a web page (Vite/React, service worker, OPFS, optional Wisp proxy for Steam and websockets). Nothing in the repo targets a desktop host, let alone Minecraft.
- craftlatro (this workspace, v0.9.1) proves the Minecraft-side half: a user-supplied commercial game running full-fidelity inside a Fabric mod via Rinku. The craftraria-specific combination (Terrarium + Rinku flat-GUI screen) is not present in any repository found.
- The upstream project itself has a standing request for exactly this shape of integration that is not planned: issue #11 "Autoloading from a generated WASM file" (host the build, load assets without a directory picker) was closed `not_planned` (https://github.com/MercuryWorkshop/terraria-wasm/issues/11).

Confidence: high for the combination; the project is an integration of two proven subsystems, not a novel engine.

## 4. Gap analysis

1. **Asset handoff into the embedded browser.** The upstream's supported copy path depends on `window.showDirectoryPicker()` (File System Access API) and OPFS writes; the Steam path needs credentials plus a Wisp proxy. Whether the File System Access API's directory picker is wired up inside JCEF/Rinku's embedded Chromium is unverified (JCEF does not necessarily implement the native dialog callbacks those APIs require). The mod's gap: a path that never asks the browser to show a picker, i.e. the mod picks the directory Java-side (reuse craftlatro's `SteamLocator` + `JFileChooser` pattern) and the served page stages assets via the simple-download flow (`fetch` a tar from the local server, extract into OPFS). The upstream code for that flow exists (`VITE_SIMPLE_DOWNLOAD`, `extractTar`) but is commented out in the build; craftraria must reproduce it in the served page.
2. **Cache layers.** The upstream build ships `sw.js`, a service worker that caches every response and re-checks COOP headers. Combined with OPFS persistence and dotnet's own resource caching, this is three cache layers where craftlatro had one (`?g=` IndexedDB cache, the cause of commit `440f734`, 2026-10-11). Serving a stale build or stale assets inside the embedded profile would present as cache-shaped bugs. Gap: a version-pinning strategy, most likely stripping or bypassing `sw.js` in the served copy (it is a web-scale optimization with no value on localhost).
3. **Save persistence.** Saves live at `/libsdl/tsaves` inside OPFS and persist inside the Chromium profile the same way love.js IndexedDB did for craftlatro. Export/import cannot reuse `SaveStore` directly: OPFS is browser-side, so the tar-in/tar-out UI must live in the served page (the upstream has an OPFS explorer with exactly that), or the mod must copy the profile's OPFS directory on disk, which is fragile and version-dependent. Unresolved at research time.
4. **Version support is narrow and pinned.** Release 1.0 (May 2025) was built by decompiling the then-current game. Issue #15 "Is it compatible with 1.4.5?" (created 2026-01-27, still open, no maintainer response) records that Terraria 1.4.5 does not work with the port (https://github.com/MercuryWorkshop/terraria-wasm/issues/15). The exact supported version (presumably a 1.4.4.x line) is not stated in the README and could not be verified from the release artifact (the version strings are compiled metadata). A Steam player on 1.4.5 will own content that may not match the port. Resolution order recorded in PLAN.md: test the pinned build against the player's actual content version first (loading is code-driven and `Content` is cumulative, so the breakage claim is testable and the evidence is thin); if it fails, the player-side remedy is a Steam depot rollback (`download_depot 105600 <depot_id> <manifest_id>`, IDs from SteamDB's depot/manifest history) into a separate folder the mod is pointed at; a player-run rebuild is not a realistic player task and a project-hosted rebuild would change the legal boundary, so it is an owner-side fallback only.
5. **Upstream defect surface.** Open, unfixed issues affect the exact paths craftraria would use: #17 "Black screen on entering a world" (native `WebAssembly.Exception` with null payload on the first batched-tile frame, reproduced on two save files on the deployed site, May 2026, open); #13 `AssetLoadException: "Images/SplashScreens/Splash_1"` (Dec 2025, open); #16 the archive-extract button is broken on the deployed site (Feb 2026, open). The mod cannot fix upstream; it can only pin a build, warn, and record repro notes.
6. **Multiplayer and mods.** Joining external servers throws on the deployed site (issue #9, closed `not_planned`); tModLoader is out of scope upstream because "performance is not good enough in dotnet interpreted/jiterpreter mode, which is required for the MonoMod WASM port to function" (README). Both match the concept's non-goals, so they are constraints, not gaps.
7. **Performance and memory budget.** The port is AOT-compiled, which the writeup credits with going from ~2 FPS interpreted to "completely usable, even on low end devices." One reporter measured ~168 MB managed heap after world load (issue #17). On top of that: the 135 MB `_framework` set streamed over localhost, the Chromium process (~150 MB runtime, Rinku's responsibility), and Minecraft's own client, with the same double-render path (Chromium offscreen surface composited by MC) that cost craftlatro ~10% fps at render scale 1.0 (`ai-docs/notes/2026-10-12-lovejs-pipeline-proven.md`, measured 144 to ~130 fps). Terraria is a fixed-60 FPS 2D game, so the budget needs measuring, not assuming.
8. **Input.** The upstream page uses `navigator.keyboard.lock()` to keep browser shortcuts from stealing game keys, and has no gamepad path at all. Keyboard lock is a web API whose availability inside Rinku's Chromium is unverified, and `RinkuBrowser` exposes no gamepad surface (craftlatro's `docs/rinku-api-notes.md` lists the full public API; there is no joystick entry). Keyboard-first is the safe v1; gamepad is an open unknown.

## 5. Foundation candidates (ranked)

1. **craftlatro (this workspace), as the structural and process template.** Fabric 1.26.2 + Rinku 3.0.4/3.0.5, `LocalHttpServer` (COOP/COEP), screen-agnostic `BalatroBrowser` singleton with parked state, `BrowserScreen`/`BrowserWindow` chrome, `CraftlatroConfig` (Cloth Config), instance-local `CraftlatroPaths`, `SaveStore`, `/craftlatro stats` diagnostics, conventional-commit and release conventions, and the AGENTS.md gotchas (never size a fresh browser via `createBrowser(url, transparent, width, height)`; never a surface larger than the window; park rather than close; one browser-affecting change per user run). Proven end-to-end 2026-10-12; v0.9.1 is on GitHub. Best foundation: it removes the entire embed class of risk. Caveat: Balatro-specific pieces (`LoveExtractor`, `LoveJsDownloader`, `GameLauncher` shims) do not transfer; the window/browser/server/config/save/stats core does.
2. **Rinku 3.0.5-26.2** (embed layer). Verified from local source branch `26.2.0`; same API surface craftlatro documented in `docs/rinku-api-notes.md` (createBrowser two-arg, `getTextureIdentifier`, `resize`, `scheduleForInit`, `CefBrowser_N.setWindowlessFrameRate`). Mature, maintained, LGPL-2.1, already a proven dependency in this workspace.
3. **MercuryWorkshop/terraria-wasm release 1.0 build** (game runtime). The only full-fidelity browser build of Terraria. Fetched at runtime from the GitHub release (the same serve-it-don't-ship-it posture as the love.js player download: `LoveJsDownloader`), cached inside the Minecraft instance, never bundled in the jar. Caveats: no license file on the repo; the artifact contains decompiled-and-recompiled Re-Logic game code; the upstream's own instruction is "Do not publicly host the game assets without permission from Re-Logic. This is for personal use only." The mod redistributes nothing (the player's own GitHub fetch supplies it), but the plan must state that explicitly. Also stale: master has newer commits than the release (the deployed site runs a different build hash), and the release is the only pinned artifact.
4. **Upstream frontend glue as reference implementation** (`src/game/index.ts`, `src/fs.tsx`, `src/splash.tsx`). Specifies, line by line, the dotnet bootstrap (`withConfig({ pthreadPoolInitialSize: 16 })`, jiterpreter runtime options, the split-wasm resource loader, module imports for the RSA and depot stubs), the OPFS staging and validation code, and the PreInit/Init/MainLoop sequence. The mod's served page reproduces this in vanilla JS (no bundler), the way craftlatro's `GameLauncher.ensureIndexHtml` writes its own index.html.
5. **r58Playz/fna-wasm-threads (MIT) and FNA-WASM-Build statics.** Only relevant if the mod ever rebuilds the port locally (e.g. to support a different Terraria version). Out of scope for v1; recorded so the option is not re-derived later.
6. **MercuryWorkshop/celeste-wasm.** Not a craftraria foundation; it is the craftleste foundation and is recorded here only to keep the family map straight.

## 6. Unknown areas

- **File System Access API inside the embedded Chromium.** Whether `showDirectoryPicker`/`showOpenFilePicker` work in Rinku's JCEF bundle (Chromium 151) is unverified. It does not need to: the design avoids browser pickers entirely (mod-side directory selection, server-side tar, page-side fetch+extract). But it should be probed early, because the upstream's OPFS explorer UI would otherwise be a dead end inside the mod.
- **OPFS inside the embedded Chromium.** Expected to work (Chromium has supported OPFS since 86, and the dotnet wasm VFS is backed by it), but unverified in this stack, and it is the linchpin of the asset pipeline. Resolve first in M1 with a probe page: create a directory, write a file, read it back through the served game page.
- **Exact supported Terraria version.** Pinned to whatever release 1.0 was decompiled from (pre-1.4.5, per issue #15). Resolution: inspect the player's `Terraria.exe` version in M3 and compare against upstream issues/commits; warn in-game when unsupported. The plan must not claim a specific version until this is measured.
- **Whether the mod can serve the upstream `_framework` unmodified through a localhost COOP/COEP server.** The hashed asset names are resolved by `dotnet.js` at runtime (`Je.locateFile` plus the boot manifest); the split-wasm resource loader is only needed for builds with 20 MB chunks. Resolution: load release 1.0's `_framework` through the server and reach the PreInit call; a failure here forces a per-build patch step (like craftlatro's `.love` repack).
- **Save export/import mechanics.** Whether the tar-in/tar-out UI lives in the served page, or the mod copies OPFS from the Chromium profile directory on disk. The upstream explorer is the reference; porting it into the mod's served page is the likely path. Unresolved.
- **`sw.js` behavior on localhost.** Whether the service worker caches served updates in a way that defeats version pinning, and whether removing it from the served copy is clean. Resolution: test an update cycle with the worker stripped versus present.
- **Performance and memory inside the MC process.** AOT wasm game + 135 MB framework + Chromium + MC, with a double render path. No published benchmark for this stack. Resolution: measure with the `/craftraria stats` analogue in M4, as craftlatro did.
- **Gamepad.** No path verified in either the upstream frontend or Rinku's API. Resolution: research JCEF gamepad support or a GLFW-level mapping in M4; keyboard-first regardless.
- **Upstream build provenance.** The deployed site runs a build newer than release 1.0 (different `dotnet.native.*` hash in issue reports). Whether release 1.0 is good enough for v1, or a build must be produced from master (which needs Linux, dotnet 9.0.4, ilspycmd 9.0.0.7889, and a matching `Terraria.exe`), is unresolved. Pinning release 1.0 is the default; the tradeoff gets recorded in `ai-docs/decisions/` per craftlatro convention.
