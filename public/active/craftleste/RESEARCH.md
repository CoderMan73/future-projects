## 1. Executive summary

Partially unique: every component needed to run Celeste in Minecraft already exists and is individually proven (the Webleste wasm port runs genuine Celeste in a browser; craftlatro already embeds a Chromium browser running a wasm game inside Minecraft 26.2), but no existing project combines them into a Celeste-in-Minecraft mod, so the integration work is real even though the novelty is the composition, not any single part. Confidence: high for component availability and for the absence of an existing mod on the searched registries (section 3); medium for unindexed projects.

## 2. Existing solutions survey

1. **Webleste (celeste-wasm), MercuryWorkshop** - https://github.com/MercuryWorkshop/celeste-wasm (default branch `threads-v2`). A "mostly-complete port of Celeste (2018) to WebAssembly, with full support for Everest mods" built on FNA-WASM-Build and MonoMod.WASM. A stub loader loads and patches the player's own Celeste.exe at runtime, so the port hosts no Celeste IP (https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/how.md). Status: active, 330 commits, 267 stars, 53 forks, 7 open issues, last push 2026-08-26 (https://api.github.com/repos/MercuryWorkshop/celeste-wasm). License: none (`"license": null` in the repository API response). Frontend reports version v1.4.0.0 (https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/frontend/src/main.tsx). Deployed demo: https://celeste.r58playz.dev/ (needs "around 1GB of memory", requires "the FNA version of Celeste", setup flow: copy local assets, extract the webleste archive).
2. **craftlatro** - the sibling mod that runs Balatro inside Minecraft via Rinku + love.js. Status: shipped, GPL-3.0, v0.9.0 and v0.9.1 released 2026-10-13 (https://github.com/CoderMan73/craftlatro/releases/tag/v0.9.1, [CL] ROADMAP.md). Its architecture (local COOP/COEP HTTP server, flat GUI browser screen, session parking, save store, instance-local paths) is the direct template.
3. **CoolElectronics' celeste-wasm build** - https://coolelectronics.github.io/celeste-wasm/. A repackaged, download-friendly build of the port ("around 1.6GB of memory", autosave with manual export, "~700MB of assets" in browser storage). Evidence that a packaged, player-supplied-assets flow works standalone; packaging reference only, no source published.
4. **LucyYuih Celeste WASM ports** - https://lucyyuih.github.io/CelesteWASMtest and https://gamejolt.com/games/CelesteWASMAndroid/1043073. Android and browser repackagings of the same port; proof the runtime travels outside its original site, irrelevant as a Minecraft foundation.
5. **Forks of the port** - https://github.com/Hyper7651/celeste-wasme and https://github.com/902-specs/celeste-wasm2 (created 2025-11-04 and 2025-09-15, same README, `threads-v2`). Derivative forks with no unique capability found.
6. **Browser-in-Minecraft libraries** - Rinku (https://github.com/Keksuccino/Rinku, source at [MS] `Rinku`, branch `26.2.0`, `mod_version=3.0.5`) and MCEF-lineage projects such as https://github.com/DimasKama/mcef-modern. craftlatro pins the published artifact `de.keksuccino:rinku-fabric:3.0.4-26.2` ([CL] gradle.properties, [CL] AGENTS.md).
7. **Celeste-named Minecraft mods** - `celestemod` (Forge 1.18.2, implements a dash, https://www.curseforge.com/minecraft/mc-mods/celestemod), `powers-of-celeste-mountain`, `Celestria` (https://modrinth.com/mod/celestria), `Celestisynth` (https://modrinth.com/mod/celestisynth), `Celestial` (sky customization, https://www.curseforge.com/minecraft/mc-mods/celestial). None embeds the Celeste game; all are name-similar mechanics mods. This is the negative evidence for section 3.
8. **Celeste classic / Celeste Classic mods** (https://github.com/CelesteClassic/CCMods) - a different, free game (Celeste Classic), not Celeste (2018); out of scope.

## 3. Uniqueness verification

- No existing Minecraft mod embeds the Celeste game. Searches across GitHub, Modrinth and CurseForge surface only the wasm ports and the name-similar mods listed in section 2 (items 5 and 7); no "celeste-in-minecraft" project was found. This is the strongest negative evidence available from public registries, and it is the claim this concept rests on.
- The buildability of the composition is positively evidenced by two working systems: craftlatro proves a wasm game running inside Minecraft through Rinku with a local HTTP server ([CL] `ai-docs/notes/2026-10-12-lovejs-pipeline-proven.md`, measured 2026-10-12), and Webleste proves genuine Celeste running in a Chromium-family browser with the player's own executable loaded and patched in-page ([CL] section 2 item 1, how.md).
- Unresolved: registry searches were done through web search, not exhaustive API enumeration of Modrinth/CurseForge/GitHub, so an obscure or very new project could be missed. Confidence remains high because any such project would have to combine these two components and would likely reference either project by name.

## 4. Gap analysis

Where the existing pieces fall short of this concept, precisely:

1. **No MC-side glue for Celeste exists.** Everything MC-side in [CL] is Balatro-specific: `.love` extraction, Lua shims, and the love.js player layout. Craftleste needs its own intake (Celeste.exe plus the Content folder), its own runtime layout (a static wasm app instead of a `player.js?g=` page), and its own in-page bootstrap.
2. **Asset intake contract.** Webleste expects the player's files in the browser's Origin Private File System: `hasContent()` requires the OPFS root to contain `Content/{Dialog,Effects,FMOD,Graphics,Maps,Monocle,Overworld,Tutorials}` plus a `.ContentExists` marker (https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/frontend/src/fs.tsx), and the loader mounts the game from `/libsdl/` with `Assembly.LoadFrom("/libsdl/Celeste.exe")` (how.md). Minecraft must bridge on-disk files into OPFS. The port's own route is browser file pickers (`showDirectoryPicker`/`showOpenFilePicker`), with an explicit note that cross-origin frames cannot open pickers (fs.tsx); behavior inside CEF offscreen rendering is unverified.
3. **Cross-origin isolation is mandatory.** The port uses .NET 9 threaded WebAssembly (`WasmEnableThreads`, `pthreadPoolInitialSize: 16`, https://github.com/MercuryWorkshop/celeste-wasm/blob/threads-v2/frontend/src/game/dotnet.ts). Emscripten gates SharedArrayBuffer behind COOP/COEP headers (https://github.com/emscripten-core/emscripten/blob/main/site/source/docs/porting/pthreads.rst), as does Chromium on desktop since Chrome 92 (https://web.dev/articles/coop-coep), and the .NET runtime expects the host to serve them (https://github.com/dotnet/aspnetcore/issues/54071). This is the same requirement craftlatro solved with COOP/COEP/CORP headers in [CL] `server/LocalHttpServer.java:149-151`, so it is a known shape, not a new problem.
4. **Runtime distribution is legally undefined.** Webleste publishes no license (section 2 item 1) and the writeup records extracting `.o` files from proprietary FMOD emscripten builds for audio (how.md). Bundling a build into the mod jar therefore crosses lines that cannot be checked; the runtime must be fetched at runtime from its official origin, the pattern craftlatro already uses for the love.js player ([CL] `downloader/LoveJsDownloader.java`, [CL] ROADMAP.md M5).
5. **Save persistence lives in browser storage.** The port autosaves into OPFS in the Chromium profile, and the packaged build warns the browser "may wipe it after a while" and offers a manual save export (https://coolelectronics.github.io/celeste-wasm/). A Minecraft-side portable save store must therefore snapshot the browser profile's storage directories, which is exactly the SaveStore approach proven in [CL] `save/SaveStore.java` (export zips `IndexedDB` directories under the Rinku cache root; import stages and applies before CEF starts).
6. **Memory budget is large and varies by packaging.** The port's README states loading consumes "600M or so" (https://github.com/MercuryWorkshop/celeste-wasm), the deployed site says around 1GB (https://celeste.r58playz.dev/), and the repackaged build says 1.6GB (https://coolelectronics.github.io/celeste-wasm/). Add Minecraft itself and the roughly 150 MB Chromium runtime ([CL] AGENTS.md) and the wasm memory sits in a browser process alongside the game. The render-scale lever from craftlatro ([CL] AGENTS.md runtime commands) is the mitigation and must carry over.
7. **Fidelity is "mostly-complete", not guaranteed 1-to-1.** The port self-describes as mostly/near complete (README, https://celeste.r58playz.dev/), and the writeup documents runtime patches and Mono/CoreCLR behavioral differences worked around along the way. The concept's "1-to-1 behavior" goal is the port's claim to load the genuine game, not a guarantee of bug parity; craftlatro handled the equivalent with a first-run fidelity warning ([CL] `ui/FidelityWarningScreen.java`).
8. **Gamepad input is unverified in the embedded browser.** Celeste is a controller-first game (SteamDB app 504230 lists "Full Controller Support", https://steamdb.info/app/504230). The browser Gamepad API inside CEF offscreen rendering is unverified; keyboard is the safe v1 default (the port also maps keyboard).
9. **Version drift.** The port has no release tags; the pinned state is a branch tip (`threads-v2`, v1.4.0.0 in the frontend). A craftleste runtime pin must be a commit hash, and every runtime change must bust the browser caches (the `.NET` runtime caches assemblies in IndexedDB the same way love.js did; the `?g=` cache-bust lesson is [CL] AGENTS.md Gotchas, commit `440f734`).
10. **Everest scope.** The port supports Everest by downloading it at runtime from `https://everestapi.github.io/everestupdater.txt` (branch `stable`, `supportsNativeBuilds=true`) and gating the Mods button on its presence (dotnet.ts, `downloadEverest`). The Minecraft side does not need to implement Everest; the question is only whether the mod's promise includes it, and the port's own UI already carries the flow.

## 5. Foundation candidates (ranked)

1. **Webleste, `MercuryWorkshop/celeste-wasm` @ `threads-v2`** - the game runtime. Fit: complete, actively maintained, loads and patches the player's own executable so it hosts no Celeste IP, runs FNA-rendered Celeste in a browser. Caveats: no license (redistribution undefined), roughly 600 MB to 1 GB load memory, targeted at Celeste 1.4.0.0's FNA build, no tags so a commit pin is required, "may encounter issues on Firefox" (irrelevant under Rinku's Chromium).
2. **craftlatro repository [CL]** - the MC-side architecture. Fit: the exact sibling, with a proven-by-measurement answer for every hard part of this plan (COOP/COEP serving, screen and input, paint rate, parking, save store, instance-local paths, stats report). Caveats: its game-specific layer (extraction, Lua shims, `player.js?g=` index page) does not transfer; its shared glue is the pattern to replicate, not code to vendor, unless the later library extraction happens first ([CL] ROADMAP.md Backlog lists that as "an architecture change, not a refactor", with the owner's follow-up to "prove it by porting a second game to Minecraft with it"). License GPL-3.0, compatible with a sibling app.
3. **Rinku 3.0.4-26.2** - the embedding. Fit: pinned and proven in craftlatro for exactly this screen shape; the local source [MS] shows the same API surface at 3.0.5 and branches for `26.2.0`/`26.3.0` plus NeoForge `26.2.0.7-beta`, so a future version matrix or loader target is a dependency question, not an architecture question ([CL] ROADMAP.md Backlog, Portability). Caveat: the 4-argument `createBrowser` overload and oversized surfaces crash the client natively ([CL] AGENTS.md Gotchas), so the known-working subset must be used.
4. **CoolElectronics' build (https://coolelectronics.github.io/celeste-wasm/)** - packaging reference only: evidence that a downloadable, asset-supplying flow works, not a code foundation.
5. **FNA-WASM-Build (https://github.com/r58playz/FNA-WASM-Build) and MonoMod.WASM (https://github.com/r58Playz/MonoMod)** - the port's toolchain. Relevant only if craftleste ever builds the port itself, which this plan does not do.

## 6. Unknown areas

1. **File System Access API inside CEF offscreen rendering.** Whether `showDirectoryPicker`/`showOpenFilePicker` surface a usable dialog inside Rinku's browser is unverified; fs.tsx itself detects cross-origin-frame restrictions. What resolves it: an M1 probe page loaded through the real mod in `runClient`. Fallback if unavailable: skip the picker entirely. The mod's own bootstrap page can write the player's assets into OPFS with `navigator.storage.getDirectory()` and `createWritable` (standard, same-origin, no dialog), then hand off to the port's index.
2. **Threaded wasm under offscreen rendering.** COOP/COEP sufficiency is documented for browsers generally (section 4 item 3); the combination of .NET threaded wasm, 16-thread pool, and CEF OSR is unverified. Resolved by an M2 probe serving any pthreads-enabled wasm page through the local server into the embedded browser.
3. **Gamepad API in OSR.** Unverified; resolved by an M3 probe page that reports `navigator.getGamepads()` state, with keyboard-first as the documented default until then.
4. **Exact OPFS contract the loader expects.** Partially documented (`/libsdl/Celeste.exe`, the `.ContentExists`/`CustomCeleste.dll` markers and the Content subfolder set in fs.tsx); the full expected layout, and how the patcher names the executable, need a real run against a player-supplied copy. Resolved at M2, recorded in `ai-docs/notes/`.
5. **Licensing and redistribution terms.** Webleste has no license file; its audio layer embeds proprietary FMOD object code. Runtime download from the official origin avoids redistribution but has not been legally reviewed. Resolved by keeping every fetch user-triggered and mod-side, hosting nothing, and treating any self-hosting as an Ask First decision; an upstream license inquiry is recommended before 1.0.
6. **Real memory ceiling inside the MC process.** Whether the Chromium/renderer cost is a subprocess budget or shared with the MC heap, on this dev machine, is unmeasured; the port exposes a memory watch callback (`CelesteLoader.WatchMemoryUsage`, dotnet.ts) that the stats report can surface. Resolved at M3/M4 by measurement, not estimation.
7. **Game canvas resize behavior.** craftlatro found Balatro/love.js sizes its canvas once at load and never follows a resize ([CL] `ai-docs/notes/2026-10-13-lovejs-canvas-sizes-at-page-load.md`). The Webleste canvas is fixed 16:9 in CSS (frontend/src/game/index.tsx), and FNA's surface behavior on browser resize is unverified. Resolved at M3; if the same behavior appears, craftlatro's notice-strip-plus-player-driven-reload pattern carries over unchanged.
8. **`navigator.keyboard.lock()` in OSR.** The port calls it while playing (dotnet.ts); availability inside CEF OSR is unverified. Impact is limited (key mapping may work without it); noted for the M3 input milestone.
9. **Rinku version line and Java floor for this project.** craftlatro's AGENTS.md stack table says Java 21, while its build.gradle compiles with `release = 25` and fabric.mod.json declares `"java": ">=25"`; Rinku's own source declares `java_version=25` ([MS] Rinku/gradle.properties). The plan follows craftlatro's working values and verifies at M1 rather than reconciling stale docs now.
